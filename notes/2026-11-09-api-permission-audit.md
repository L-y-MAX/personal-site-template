做《示例项目》联调的时候，我才第一次注意到「权限」有多容易漏。
一开始我以为接口加了登录校验就安全了。

后来才发现，**登录校验和授权完全是两件事**。加了 `login_required` 只说明「这个人是登录用户」，
不代表「这个人可以看这条数据」。

这篇是我整理的一份自查清单，四个检查点，按顺序过一遍。

## 一、身份校验：有没有登录

最基础的一层。Django 里有两种写法：

```python
from django.contrib.auth.decorators import login_required

@login_required
def profile(request):
    ...
```

DRF 里更常见的是在 `permission_classes` 里统一加 `IsAuthenticated`。

这一层只解决「你是谁」，不解决「你能做什么」。

## 二、归属校验：这条数据是不是你的

最容易出问题的一层。典型写法：

```python
# 看起来没问题，其实谁都能传别人的 id
report = Report.objects.get(pk=request.GET["id"])

# 正确做法：把用户条件拼进查询里
report = Report.objects.get(pk=request.GET["id"], owner=request.user)
```

第二行的区别是：查不到的时候会抛 `DoesNotExist`，而不是把别人的数据查出来再「假装检查」。

**不要**写成先查再 `if report.owner != request.user: return 403`——
能查出来就说明数据已经离开数据库了，多一次判断只是心理安慰。

## 三、角色边界：管理员能不能越界

学生 / 管理员两套接口，如果共用同一个 `get_queryset`，很容易出现「学生账号能调到管理员的接口」。

检查点：

- 管理端接口是不是独立的路由前缀
- 权限类是按视图配置的，还是全局加了一次就以为够了
- 有没有接口同时暴露给学生端和管理端

## 四、写操作：更新和删除要二次确认

读接口漏了归属校验，最多是信息泄露；**写接口漏了，就是可以直接改别人的数据**。

几个高危动作：

1. `PUT` / `PATCH` 时用请求体里的 `id` 定位记录；
2. 批量删除接口没有限制 `owner`；
3. 上传接口返回的 URL 可以被任意用户后续引用。

统一做法：所有按 id 操作的地方，都把 `request.user` 作为查询条件的一部分，而不是事后判断。

## 自查清单

- [ ] 每个接口都知道自己属于哪一层权限
- [ ] 所有按 id 查询的地方都带上了用户条件
- [ ] 管理端接口独立前缀 + 独立权限类
- [ ] 写接口用 `PATCH` 而不是「什么字段都接受」的 `POST`
- [ ] 用一个普通账号，去请求一遍所有接口，看能拿到什么

最后一条最有用：**用低权限账号把接口跑一遍**，比读十遍代码快。
